6. **FIXED — `EditCustomerProfile.js` mis-split a two-word first name.** `customer_name.split(' ')` took only `names[0]` as First Name; a first name with a space (e.g. `"<prefix> Mary Ann"`) showed up as First Name = `"<prefix>"`, Last Name = everything else. The adjacent comment showed the multi-word-*last*-name case was already handled (by splitting on the *first* space); the symmetric first-name case wasn't. `handleSubmit` reassembles `${firstName} ${lastName}`, so this never corrupted the saved value — it was a pure misdisplay. **Fix:** now prefers separately-stored `customer_first_name`/`customer_last_name` fields if the profile ever provides them (defensive — the `customers` table only stores a combined `customer_name` today, confirmed via schema, so this branch is currently always skipped), otherwise splits `customer_name` on the *last* space instead of the first. This is a deliberate, task-directed trade-off, not a free lunch: a name that's multi-word on *both* sides (e.g. this suite's `createCustomer()` fixture, `"<prefix> Mary Ann" + "Van Buren"`) cannot be split back unambiguously either way without a stored field — splitting on the last space now correctly recovers a multi-word FIRST name (the defect being fixed) but no longer recovers a multi-word LAST name paired with a single-word first name the way the old first-space split happened to. Documented in code comments and in a dedicated jest test (`a name that is multi-word on both sides cannot be split back exactly`). Tests: a new Playwright test creates a customer with an unambiguous two-word-first/one-word-last name directly (rather than reusing `createCustomer()`'s inherently-ambiguous fixture) and confirms the split; 5 new jest tests in `EditCustomerProfile.test.js` cover the split, the no-space case, and the stored-fields branch.

## What changed under this suite mid-session (shared sandbox)

This DS2 checkout, Postgres sandbox and MinIO instance are shared with at least one other concurrent process during this session. Confirmed, real changes that required adapting shared helpers (all in `lib/`, not weakening any assertion):

- **`CreateInvoiceGrid.js` was rewritten** to a controlled `rowSelectionModel` with MUI's own default checkbox-selection column. MUI's built-in per-row checkbox has a state-dependent accessible name (`'Select row'` unchecked, `'Unselect row'` checked — `@mui/x-data-grid`'s `localeTextConstants.js`), so a locator built once against `{name:'Select row'}` stops resolving the instant a click actually succeeds. `lib/ui.js`'s `selectInvoiceRow()` now targets the stable `.MuiDataGrid-cellCheckbox` class instead.
- **A second, real fixture user named "Eliza Smith"** (`user_id` 90047, a different email) appeared in account 9001 partway through the session, created by the other concurrent process's own testing (confirmed via `SELECT ... FROM users`). `lib/ui.js`'s `choose()` now takes `.first()` on an exact-text option match — this suite's own fixture (90011, lower id, first in option order) is unaffected, and this only changes behavior when a genuine duplicate is present.
- **Job Categories and Work Descriptions accumulated ~20 rows each** from the same concurrent process, enough to push a freshly-created row onto a page `DataGridTable`'s default `pageSize=5` doesn't show. `master-data.spec.js` now applies the grid's existing quick filter before checking row visibility.
- **The time-tracker upload S3 key format changed** to be account-and-owner-scoped (`.../processed/<account_slug>_<accountID>/user_<id>/...`, replacing a flat `.../processed/Person_Admin/...` layout — see `timeTracking-router.js`'s `buildProcessedPrefixes`, a real fix for a same-named-employee collision risk across accounts). `lib/storage.js`'s cleanup key reconstruction (used by the standalone `node lib/cleanup.js <prefix>` recovery path) now builds the current primary prefix and still recognizes the former layout.
- **`CreateNewInvoices.js` was rewritten** to stop auto-clearing the finalize result after 2 seconds, use a real dismissible `Alert`, and show each skipped customer's existing invoice number — exactly the change `month-end.spec.js`'s "same-day skip feedback" test was written in anticipation of. It's confirmed landed and the test now asserts it directly (close button, invoice number in the skip message) instead of the old conditional-on-source-text `test.fixme`.
- Two further **timing hardenings**, not tied to a specific product change but needed once the suite ran repeatedly against a busier shared backend: `lib/ui.js`'s `finalize()`/`invoicePreview()` retry their initial customer-row search (`findInvoiceRow()`) rather than trusting the Create Invoice page's one-shot outstanding-balance fetch on the first try.

None of the above weakens a business assertion — every one of these is a locator/timing adaptation to a real, confirmed change in the thing being tested, verified by re-running the affected spec(s) repeatedly (including immediately before and after each fix) until stable.
